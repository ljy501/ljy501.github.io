> This article walks through how we scoped, decomposed and scheduled a 20-person library management system project — from a signed project charter to a go-live plan — using WBS decomposition, a RACI responsibility matrix, a critical-path network diagram and a Gantt chart. No single line of business code, but everything that decides whether a software project actually ships on time.

## 一、前言：不是代码难，是"怎么排"难

做一个图书馆图书管理系统，技术本身并不性感：图书借还、检索、统计报表、对接校园一卡通，典型的 CRUD + 报表系统。真正的难点在于：**这是一个甲方乙方双方、20 人团队、横跨 4 个月的项目**：需求方是图书馆，要的是"手工录入错误率降一半、借阅流程压到 5 分钟以内、读者满意度 90% 以上"；开发方要在预算和工期内把系统做出来、服务器装完、培训完、平稳上线。

代码写歪了可以改，**进度排错了，交期就是灾难**。这一篇复盘我作为技术主管参与的整套项目排期方法：怎么把一个模糊的"做系统"拆成 23 项可执行任务，怎么算出哪条路径真的决定工期，以及怎么用甘特图把它们钉到时间轴上。

## 二、环境与架构：先把"要做什么"钉死

项目开工的第一件事不是写代码，而是签**项目章程**：把目标、范围、约束写死，双方签字画押。

| 维度 | 内容 |
|---|---|
| 功能范围 | 图书管理、读者服务（预约/续借）、统计分析三大模块 |
| 技术架构 | 微服务拆分模块，IDEA 编码，单元测试 + 集成测试覆盖率 ≥ 85% |
| 非功能指标 | 系统响应时间 ≤ 2 秒；对接校园一卡通接口 |
| 硬约束 | 预算封顶、2025-09-01 前正式上线、符合图书馆信息化安全规范 |
| 团队构成 | 前端 2 人、后端 4 人、测试 4 人、运维 5 人、采购 3 人、产品/项目经理 2 人 |

范围一旦以《需求说明书》为基准冻结，后续任何加需求都必须走变更流程，这是后面排期不被反复推翻的前提。

## 三、Step 1：WBS 工作分解，把"系统"拆成可执行任务

排期的第一性原理：**任务不拆到"一个人三天能干完"的粒度，就不可能估准工期**。我把项目从上到下拆了三层：

```text
图书馆图书管理系统项目
├── 需求调研（32天，5人）
├── 系统开发
│   ├── 后端：图书检索/借书/还书/借阅记录/余量统计/热门统计/逾期交款/读者反馈（各3天）
│   ├── 前端：首页界面/读者界面（各6天）、搜索结果界面（3天）、绑定控件与模块代码（2天）
│   └── 测试：基础功能测试（6天）、安全测试（5天）
├── 硬件集成：服务器采购(12天)/安装(3天)/调试(9天)，其余设备采购(10天)/调试(4天)
└── 培训与运维：讲解系统功能(9天)、技术支持(15天)
```

每个工作包括号里都标了负责人数：**人是成本，也是资源约束**：后端模块看似 8 个并行 3 天就能做完，但后端小队只有 4 个人，排期时必须按资源平滑过一遍。

![项目 WBS 详细分解图（括号内数字为该工作包安排人数）](/images/library-wbs-detail.jpeg)

*WBS 全景：蓝=需求调研，绿=后端，红=前端/测试，紫=硬件，橙=培训运维，每个叶子节点都是一个有工期、有人头的可执行任务*

## 四、Step 2：定责任，RACI 矩阵消灭"三个和尚"

任务拆完，下一个必踩的坑是**责任真空**：出了问题大家都说"这不是我负责"。解法是 RACI 矩阵：每个活动标四类角色，R（执行）、A（最终负责）、C（被咨询）、I（被告知）。

| 活动 | 甲方角色 | 乙方角色 | RACI |
|---|---|---|---|
| 需求调研 | 业务负责人 | 项目经理 | 甲方 A / 乙方 R |
| 借书、还书模块 | 业务负责人（知会） | 后端小队 | 甲方 I / 乙方 R |
| 安全测试 | 业务负责人（负责） | 测试组 | 甲方 A / 乙方 R |
| 服务器调试 | 业务负责人（负责） | 硬件组 | 甲方 A / 乙方 R |
| 技术支持 | 系统管理员（咨询） | 培训支持 | 甲方 C / 乙方 R |

原则只有一条：**每个活动有且只有一个 A**。评审会上这条表格一过，再也没人问"这块谁跟"。

## 五、Step 3：关键路径，找出真正决定交期的那条链

23 个活动（A–W）之间存在依赖关系：绑定控件（N）必须等读者界面（L）和后端 G/H/I/J 全部完成；基础功能测试（O）等 N；安全测试（P）等 O；服务器安装（R）等采购（Q），调试（S）等 R……把这些依赖画成网络图，每条边标上工期：

![项目网络图，红色路径即关键路径](/images/library-network-critical-path.png)

*节点是活动，边上的数字是工期天数；红色实线连成的就是关键路径，上面任何活动拖一天，整个项目就晚一天*

算下来关键路径是：**需求调研 A(32) → 前端链 K/L → N → O → P → 硬件链 Q → R → S → U → 技术支持 W(15)**。这条链上总工期最长，所以我们对它的监控密度最高：每周站会只追关键路径上的活动，非关键路径活动有浮动时间，可以容忍小幅滑动。

![项目甘特图：23 项任务按时间轴排布](/images/library-gantt-chart.png)

*甘特图把网络图落到日历上：5/10 需求调研开工，7 月集中开发与硬件调试，8 月培训与试运行，9/1 正式切换上线*

## 六、Step 4：成本估算与变更控制

排期之外还要算钱。按"时间换金钱"的思路做资源加权估算：

| 预算项 | 估算成本 | 说明 |
|---|---|---|
| 工资 | 700,000 元 | 20 人 × 7,000 元/月 × 5 个月核心开发期 |
| 咨询和采购服务费 | 150,000 元 | 服务器 3 台、扫描终端 5 台、存储、软件许可与数据库授权 |
| 差旅费 | 10,000 元 | 需求调研、硬件验收、培训支持的交通住宿 |
| 折旧 / 租金 / 其他 | 60,000 元 | 硬件折旧、机房租赁、培训资料与办公用品 |
| **总成本** | **920,000 元** | — |

![项目成本预算表](/images/library-budget-plan.png)

*成本计划明细：人力占比超过七成，这印证了软件项目"人是最大成本"的常识*

变更控制走标准四步：提交《变更单》→ 双方评估对成本、进度、技术可行性的影响 → 变更委员会审批签补充协议 → 更新项目计划与文档。没有书面确认，任何口头加需求都不排期。

## 七、踩坑实录

**坑 1：活动工期估成"单人理想值"，没扣资源**
最初把 8 个后端模块排成并行 3 天，画在图上很漂亮，但后端只有 4 个人，同一时间最多并行 4 个任务。重新按人头串行+并行混排后，后端链路整体后移了约一周。教训：**工期估算 = 任务工时 ÷ 可用资源数**，不是画图好看。

**坑 2：依赖关系只写"谁等谁"，漏了跨团队等待**
一度把"信息录入和备份（B）"排在 7 月底就开始，后来才发现它依赖安全测试（P）和服务器调试（S）双双完成，数据要录进新服务器，且安全测试过关。把这种跨团队依赖补进网络图后，B 的位置从 7/26 挪到了 8 月。教训：**依赖清单要逐条对着网络图检查，不能只在脑子里想**。

**坑 3：预算约束和成本估算"两张皮"**
项目章程里写的是预算封顶，而详细成本计划算下来总成本 92 万，人力一项就 70 万，估算远超早期拍脑袋的上限。处理方式不是砍功能，而是把估算摆上桌面重新校准：哪些岗位可以共用、哪些硬件采购价可以谈、试运行支持期能否压缩。**先承认数字冲突，再谈怎么收敛**，比硬撑着不看强得多。

## 八、总结与思考

这一个项目我没写多少业务代码，但把完整的项目管理链路走了一遍：**章程定边界 → WBS 拆任务 → RACI 定责任 → 网络图找关键路径 → 甘特图排日历 → 变更流程兜需求蔓延**。最终里程碑是六段式：需求调研（5/10–6/10）→ 设计开发（6/15–7/31）→ 硬件部署（6/30–7/25）→ 测试优化（6/30–7/11）→ 培训试运行（8/1–8/24）→ 9/1 正式上线。

回头看最大的收获：**排期不是预测未来，而是把不确定性显式化**，关键路径上的活动暴露出来了，才知道该盯哪里；成本和预算的差距摆出来了，才知道该谈什么。这套方法以后带到任何中大型项目里都通用。
